# 배포 실행 — Railway 단일 서비스 (v1, 2026-08-27)

- 대상: 명세 §2.0의 **배포 단위 1개**(FastAPI가 `dist`·`/api`·`/admin`을 함께 서빙)를 상시
  구동 상태로 올린다.
- 앞선 문서와의 관계: 자산을 **어떻게 넣는가**는 `docs/배포_자산_반입_v1.md`(PH-04)가 정본이다.
  이 문서는 **그 앞뒤**를 다룬다 — 서비스·DB를 세우고, 검증하고, 세션 운영으로 넘긴다.
- 이 배포를 하는 이유: 인터뷰 세션을 **연구자 2인이 각자 진행**한다. 로컬 터널(ngrok 등)은
  호스팅하는 사람의 노트북이 깨어 있어야 하고, 절전·네트워크 전환 한 번이면 세션 중
  참가자 화면이 끊긴다 — §9.1이 막는 dead-end를 운영 층위에서 만드는 구성이다.

## 1. 이미 검증된 것 (로컬 실측, 2026-08-27)

아래는 **배포 전에 로컬에서 실제로 돌려 확인한 결과**다. 배포에서 처음 만나는 미지수를
줄이려고 미리 때려본 것이므로, 여기 적힌 것은 콘솔에서 다시 고민하지 않아도 된다.

| 확인한 것 | 방법 | 결과 |
|---|---|---|
| 이미지 빌드 | `docker build .` | 성공 · 354MB |
| Postgres DDL | `init_db.py` → PG 16 | 16 테이블 생성 |
| **세션 전 구간** SS00→SS10 | Postgres 대상 full-flow(FakeLLM) | 14/16 테이블 기록 · 완주 |
| 🔒 필드 | `turns.text` = `bytea` | Fernet 토큰으로 저장 · 평문 없음 |
| **transaction-mode 풀러** | pgbouncer 1.25 경유 full-flow | 완주 · 반복 25회 prepared statement 문제 없음 |
| 볼륨 오버레이 | 스테이징 산출물을 `/data`로 마운트 | 실값 3건 + 더미 21건 정상 · 「자산 출처」 일치 |
| 콘솔 인증 | `/admin/console` | 무인증 401 · Basic auth 200 |
| Railway CLI 문법 | v5.44.1 실측 | `volume files upload/download/list` 확정 |
| 로컬→PG 데이터 이관 | 580행 이관 후 복호화 | 시각·암호문 무손실 |

두 가지는 **로컬에서 확인할 수 없어 배포 후에 봐야 한다**: Supabase 실제 접속(아래 2.2의
호스트·포트 조합)과 OpenRouter 실모델 응답([확인 1]).

## 2. 사람이 외부 사이트에서 해야 하는 일

순서가 중요하다. 특히 **2.4의 자산 반입이 끝나기 전에 `ASSIGNMENT_PATH`를 설정하면 기동이
끊긴다**(반입 문서 §2 규칙 3).

### 2.1 Railway — 프로젝트·서비스

1. <https://railway.com> 가입(GitHub 계정으로). 무료 체험 한도를 넘기면 상시 구동이 안 되므로
   **Hobby 플랜으로 올린다**(카드 등록). 실제 청구액은 콘솔의 Usage에서 확인한다.
2. 리포를 붙인다. 둘 중 하나:
   - **GitHub 연동**(권장) — `New Project → Deploy from GitHub repo` →
     `whodeeboiiii/when-support-doesnt-fit-study2`, 브랜치 `main`. 이후 push할 때마다 자동
     재배포된다.
   - **로컬 업로드** — `railway up`. GitHub를 거치지 않는다.

   > ⚠ **GitHub 연동은 `origin/main`을 빌드한다 — 작업 트리가 아니다.** 2026-08-27 기준 로컬에
   > 미커밋 변경이 42파일 1,298줄 있다(프롬프트 v3.1 개정·P00 문면·화면 문안 등). 이 상태로
   > GitHub 연동 배포를 걸면 **파일럿 조정 이전 버전이 배포된다.** 연동 배포 전에 반드시
   > `git push`하고, 배포된 커밋 해시를 `railway logs -b`로 대조하라. 커밋하고 싶지 않은
   > 단계라면 `railway up`(로컬 디렉터리 업로드)을 쓴다.

3. Railway가 리포 루트의 `Dockerfile`을 자동으로 잡는다. Build 설정을 따로 만들지 않는다 —
   `Dockerfile`이 플랫폼 중립이어야 한다는 것이 그 파일의 전제다.
4. **리전** = `Southeast Asia (Singapore)`. **Railway에 서울 리전은 없다** — 2026-08-27
   기준 지원 리전은 US West·US East·EU West·Southeast Asia(싱가포르) 넷이고 아시아는
   싱가포르 하나뿐이다. 연구팀 결정은 "서울"이었으나 이 호스트에서는 불가능하므로 가장
   가까운 싱가포르로 두고, **dossier 실값 볼륨이 싱가포르에 있다는 사실을 IRB 기록에
   남긴다**(2.7). 국내 잔류가 요건이 되면 호스트를 바꿔야 한다(Dockerfile은 플랫폼
   중립이라 Cloud Run `asia-northeast3`·Fly.io `icn` 등이 같은 이미지를 받는다).
5. **Health check path**를 `/api/health`로 설정한다. 자산 게이트(§5.4)가 실패하면 기동이
   끊기도록 설계돼 있으므로, 헬스체크가 깨진 배포를 살아 있는 것으로 오인하지 않게 한다.

> `PORT`는 Railway가 주입한다. 직접 만들지 않는다(Dockerfile의 `CMD`가 `${PORT:-8000}`을 읽는다).

### 2.2 DB — Supabase Postgres (명세 §2.1)

명세가 배포 DB를 **Supabase Postgres(서울)** 로 못박고 있다. Railway가 제공하는 Postgres
플러그인으로 바꾸면 세팅이 몇 분 짧아지지만 그건 **명세 변경**이므로 여기서 임의로 바꾸지
않는다. 바꾸고 싶으면 §2.1을 고치고 결정을 기록한 뒤에 한다.

1. <https://supabase.com> 프로젝트 생성 — **Region: Northeast Asia (Seoul)**.
2. DB 비밀번호를 생성하고 **비밀번호 관리자에 보관**한다. 이후 재확인이 불가능하다.
3. `Project Settings → Database → Connection string`에서 URL을 복사한다.
   **Session pooler** 쪽을 쓴다(호스트가 `…pooler.supabase.com`, 포트 `5432`).
   - Direct connection은 IPv6 전용일 수 있어 호스트에 따라 붙지 않는다.
   - Transaction pooler(포트 `6543`)도 코드상 문제는 없다 — 트랜잭션마다 `search_path`를
     다시 걸도록 짜여 있고(`models/session.py`), 로컬에서 pgbouncer transaction 모드로
     완주까지 확인했다. 다만 **보수적으로 session pooler를 기본으로 둔다.**
4. URL 형태는 `postgresql://postgres.<ref>:<password>@…pooler.supabase.com:5432/postgres`이다.
   **그대로 붙여도 된다** — 드라이버가 빠진 형태를 앱이 psycopg3로 정규화한다(`core/config.py`).

### 2.3 환경변수 (Railway 서비스 → Variables)

`.env.example`이 전 항목의 정본이다. 배포에 넣을 값:

| 변수 | 값 | 비고 |
|---|---|---|
| `DATABASE_URL` | 2.2에서 복사한 URL | 비밀 |
| `DB_SCHEMA` | `proto_v2` | 본실험 전환 시 `main_v2` |
| `STUDY_VERSION` | `proto_v2` | 위와 함께 바꾼다 |
| `DEV_MODE` | `false` | **true면 원격 DB에서 기동이 거부된다**(§0.5) |
| `OPENROUTER_API_KEY` | 로컬 `.env`와 동일 | 비밀 |
| `MAIN_MODEL_ID` | `anthropic/claude-opus-4.8` | [확인 1] 슬러그 재확인 |
| `VALIDATOR_MODEL_ID` | `openai/gpt-5.4` | [확인 1] |
| `LLM_CONCURRENCY` | `2` | §0.5 |
| `AI2_TIMEOUT_MS` | `90000` | §0.5 |
| `CHECKER_TIMEOUT_MS` | `45000` | §0.5 |
| `ADMIN_USER` / `ADMIN_PASS` | 콘솔 자격 | 비밀 · 아래 4절 참조 |
| `FERNET_KEY` | **로컬 `.env`와 반드시 동일** | 아래 경고 |
| `DISCORD_WEBHOOK_URL` | (선택) | §2.8 운영 알림 |
| `DOSSIER_DIR` | `/data/dossiers` | 2.4 이후 |
| `ASSIGNMENT_PATH` | `/data/assignments/assignment_v1.json` | **2.4 반입 이후에만** |

> ⚠ **`FERNET_KEY`는 로컬 `.env`의 값을 그대로 옮긴다.** 이미 로컬에 파일럿 세션 2건의
> 🔒 데이터(User1·AI2·sidecar)가 그 키로 암호화돼 있다. 새 키를 만들면 그 데이터를 영원히
> 읽을 수 없고, 이관도 무의미해진다(§2.9 — "수집 시작 후 변경 금지").

CLI로 넣을 때 비밀값이 셸 히스토리에 남지 않게 하려면:

```bash
railway variable set DB_SCHEMA=proto_v2 --skip-deploys
grep '^FERNET_KEY=' .env | cut -d= -f2- | railway variable set FERNET_KEY --stdin --skip-deploys
```

### 2.4 볼륨 + 자산 반입

`docs/배포_자산_반입_v1.md` §3이 정본이다. 요약하면:

```bash
railway volume add --mount-path /data                       # 최초 1회
python scripts/stage_volume_assets.py --out .volume_staging # 검증 + 반입본
```

**올린 뒤에** `DOSSIER_DIR`·`ASSIGNMENT_PATH`를 설정하고 재배포한다.

### 2.5 도메인

`Settings → Networking → Generate Domain`(또는 `railway domain`). `…up.railway.app` 형태의
HTTPS 주소가 나온다.

> ⚠ **HTTPS여야 한다.** 세션 쿠키가 배포 구성에서 `Secure`로 나가므로(`api/deps.py`), 참가자가

참가자 링크 = `https://<도메인>/` · 연구자 콘솔 = `https://<도메인>/admin/console`.

## 3. 배포 후 검증 (순서대로, 전부 통과해야 세션을 연다)

```bash
# ① 기동·자산
curl -s https://<도메인>/api/health | python -m json.tool
railway ssh -- python scripts/freeze_study_version.py --check

# ② 콘솔 인증
curl -o /dev/null -w '%{http_code}\n' https://<도메인>/admin/console            # 401
curl -o /dev/null -w '%{http_code}\n' -u USER:PASS https://<도메인>/admin/console # 200

# ③ 로그
railway logs -d | tail -40
```

확인할 것:

1. `/api/health`의 `dev_mode: false` · `db_schema` · `assignment.is_dummy: false`.
2. 「자산 출처」에 `(DOSSIER_DIR 오버라이드)` 표시와 `lock N건`.
3. 기동 로그에 `created 16 tables`(첫 배포) 또는 그에 준하는 정상 기동.
4. **P00으로 QA 워크스루 1회**(§10.2) — 실LLM으로 SS00→SS10을 한 번 끝까지 통과시킨다.
   이것이 통과하기 전에는 실참가자 세션을 열지 않는다.

## 4. 세션 운영 — 연구자 2인 구성

- 참가자에게는 `https://<도메인>/`만 보낸다. 접속 코드는 콘솔에서 세션을 만들 때 나온다.
- 연구자는 `https://<도메인>/admin/console`에 Basic auth로 붙는다. 두 사람이 동시에 붙어도
  된다 — 서로 다른 참가자의 세션을 각자 진행할 수 있다.
- ⚠ **콘솔 계정이 하나뿐이다.** §2.7이 HTTP Basic 단일 자격으로 정의돼 있어, 두 연구자가
  같은 `ADMIN_USER`/`ADMIN_PASS`를 공유한다. `audit_logs`에 행위는 남지만 **누가 했는지는
  구분되지 않는다.** IRB 문안 4항("접근 기록을 보존한다")을 로그로 만족시키려면 둘 중 하나를
  정해야 했다: (ㄱ) 세션 진행자를 연구 기록에 수기로 남긴다, (ㄴ) 계정을 분리한다.
  **2026-08-27 결정: 계정을 분리하지 않는다(ㄱ).** 코드·명세 변경 0건. 대신 **세션마다
  진행자를 연구 기록에 남기는 것이 IRB 문안 4항의 이행 수단**이 되므로, 세션 로그에
  진행자 이름을 반드시 기입한다.

## 5. `proto_v2` → `main_v2` 전환

QA 워크스루가 통과하고 모집을 시작할 때:

1. `DB_SCHEMA`·`STUDY_VERSION`을 `main_v2`로 바꾼다.
2. 재배포하면 `init_db.py`가 새 schema에 테이블을 만든다(`CMD`에 들어 있다).
3. `proto_v2`는 **읽기 전용으로 남긴다** — 지우지 않는다. QA 기록이다.
4. `freeze_study_version.py --check`를 다시 돌려 모집 게이트를 확인한다.

**Alembic은 없다.** 스키마 변경은 새 schema로 갈아타는 방식이고, 본실험 시작 후에는
§1.4에 따라 변경 자체가 금지다.

## 6. 로컬 파일럿 데이터를 옮길 것인가

로컬 `proto_v2_local.sqlite3`에 세션 2건이 있다 — **P08(완주, SS10)** 과
**P23(진행 중, SS08 · status=active)**.

- 옮기지 않으면: 배포 DB에는 이 둘이 없다. P08의 데이터는 로컬에만 남고(export 시 두 곳을
  합쳐야 한다), **P23은 배포에서 재개할 수 없다** — 참가자가 다시 접속해도 세션이 없다.
- 옮기려면:

```bash
python scripts/migrate_local_to_deploy.py \
    --source proto_v2_local.sqlite3 \
    --target "<DATABASE_URL>" --target-schema proto_v2        # 미리보기
python scripts/migrate_local_to_deploy.py ... --apply          # 실제 이관
```

  대상 schema가 비어 있어야 돈다(두 번 돌려 겹치는 것을 막는다). 시각은 UTC로 명시해 옮기고,
  🔒 필드는 암호문 그대로 간다 — **`FERNET_KEY`가 같아야 읽힌다**(2.3의 경고).

**2026-08-27 결정: 옮긴다.** 실행 시점은 **2.2(Supabase 생성)와 2.3(환경변수) 이후**다 —
대상 DB가 있어야 돌기 때문이다. 대상 schema(`proto_v2`)가 비어 있는 상태, 즉 **첫 배포 직후
아무 세션도 만들기 전에** 돌린다. 이관 후 콘솔 R1에서 P08·P23이 보이는지 확인한다.

⚠ P23은 `active`(SS08) 상태로 옮겨진다 — 참가자가 다시 접속하면 그 자리에서 이어진다.
재개할 계획이 없다면 이관 후 콘솔에서 별도로 처리한다.

| `AssignmentContractError: ASSIGNMENT_PATH=…` | 반입 전에 변수부터 설정 | 파일을 올린 뒤 재배포 |
| 참가자가 P0에서 못 넘어간다 | `http://` 링크 | `https://`로 다시 보낸다(2.5) |
| 세션 중 AI2 실패 | LLM 오류 | §9.1대로 `neutral_fallback`으로 수렴한다. 콘솔 R2에서 상태 확인 |
| 배포가 세션 중에 재시작됐다 | push로 인한 자동 재배포 | **모집 기간에는 `main`에 push하지 않는다**(아래) |

> ⚠ GitHub 연동을 쓰면 `main`에 push할 때마다 재배포되고 **진행 중인 세션의 커넥션이
> 끊긴다.** 세션 데이터는 DB에 있어 잃지 않지만 참가자 화면은 순간 끊긴다. 모집 기간에는
> push를 멈추거나, 자동 배포를 꺼 두고 수동 배포로 돌린다.
